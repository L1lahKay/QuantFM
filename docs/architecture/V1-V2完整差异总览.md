# QuantFM V1 / V2 完整差异总览

> 核验基线：2026-07-31。本文以当前代码、配置和本地 checkpoint 为准，集中整理
> V1/V2 的数据、Token、模型、Loss、MoE、表征和 artifact 差异。
>
> 最重要的边界：**V1/V2、Dense/MoE、旧/新 Ranker 是三条相互独立的版本轴**。
> 不能看到 `MoE` 就称为 V2，也不能看到 `gated_sum` 就称为 V2。

## 1. 先给结论

QuantFM V2 不是一次单纯的 Transformer 扩容，而是一次完整的数据和训练语义升级：

```text
V1
cn_l2_v1
  → vocab.json / 单离散 token 通道
  → 固定全局字段列表
  → 字段 embedding 求和
  → 6 路等权 next-event CE
  → flat mean 股日 embedding

V2
严格因果 replay + cn_l2_v2
  → vocab_v2.json / FieldSpec
  → token + normalized scalar 双通道
  → gated/scaled/concat 字段融合
  → 熵归一化、多任务 mask、ordinal next-event Loss
  → 跨 chunk 正确的多尺度股日 embedding
  → 可选 Temporal Regime-MoE / Backbone-MoE
```

但当前必须把“设计完成”和“实证完成”分开：

- V1 是已有正式数据与多档 checkpoint 的稳定兼容链；
- V2 的 schema、Tokenizer、Loss、模型、审计和配置代码已经落地；
- 本地只有 5-update 的 V2 base smoke，不是 FULL 盘口 V2 正式训练；
- 正式 V2 25M/100M/230M、V2 Backbone-MoE、多 seed 和新 untouched OOS 尚未完成；
- 本地 Backbone-MoE V1 已完成 50,000 updates，但它仍使用 V1 Token 和 V1 Loss，
  不能当成 V2 MoE 结果。

## 2. 三条版本轴必须分开

| 版本轴 | 可选项 | 决定什么 |
|---|---|---|
| 数据/Tokenizer/FM artifact | V1 / V2 | schema、字段、特殊 ID、分箱、scalar、预训练 Loss、checkpoint 合约 |
| Backbone | Dense / Backbone-MoE | Transformer FFN 是单个 Dense SwiGLU，还是 shared + routed experts |
| 股日适配 | 无 / Temporal Regime-MoE | 是否在日内聚合后按显式 regime 特征选择专家 |
| 下游 Ranker | legacy / artifact v2 | 选股标签、Top-K Loss、验证选择和生产 artifact 合约 |

当前仓库里的典型组合说明了为什么不能混称：

| 实验 | Token/Loss | Fusion | Backbone | 盘口 | 正确称呼 |
|---|---|---|---|---|---|
| `dense_230m_v1` | V1 / 六路等权 CE | `gated_sum` | Dense | 无 | Dense230M V1 compatibility baseline |
| `backbone_moe_v1` | V1 / 六路等权 CE | `gated_sum` | Backbone-MoE | 无 | Backbone-MoE V1 |
| `v2_25m_smoke` | V2 / normalized + ordinal | `gated_sum` | Dense | 无真实盘口 | V2 base 工程 smoke |
| `config_v2_230m.yaml` | V2 | `gated_sum` | Dense | FULL V2 目标 | 正式 Dense V2 候选配置 |
| `config_v2_backbone_moe*.yaml` | V2 | `gated_sum` | Backbone-MoE | FULL V2 目标 | V2 MoE 候选配置 |

因此，`gated_sum`、显式 `ffn_hidden`、新的训练计数和 Backbone-MoE 都能运行在 V1
artifact 上；真正定义 FM V2 的是完整的 V2 数据、vocab、FieldSpec、TargetSpec 和
artifact 契约。

## 3. 全量差异矩阵

| 层级 | V1 | V2 | 影响 |
|---|---|---|---|
| 事件 schema | `cn_l2_v1` | `cn_l2_v2` | V2 强制版本化因果盘口字段 |
| 事件顺序 | 历史产物可能是 `local_time_v1` | 要求显式稳定排序语义 | 防止同时间事件倒序和未来信息混入 |
| 参考价语义 | 历史产物可能使用未来回填 EW-VWAP | 要求显式、可审计的因果初始化 | 旧 shard 不能补 metadata 假升级 |
| 盘口状态 | 无逐事件盘口 | 事件后 post-state；事件价格距离用 pre-state | 模型能看到价差、深度和不平衡 |
| 字段定义 | 全局 tuple 分散在代码中 | 有序 `FieldSpec` 写入 vocab/checkpoint | 输入、目标和字段顺序不再隐式漂移 |
| 基础输入字段 | 9 个 token 字段 | 默认 6 个基础字段；FULL 再加 9 个盘口字段 | 删除低信息或伪推断字段，增加微观结构上下文 |
| 目标字段 | 6 个 | 默认 5 个 | V2 的 `session` 只输入、不预测 |
| 特殊 token | 仅 `PAD=0` | `PAD/UNK/NA/BOS/EOS/SESSION_BREAK=0..5` | 缺失、未知、padding 不再混淆 |
| 连续值 | 仅 32-bin token | bin token + 标准化 scalar | 保留桶内精细信息 |
| 缺失连续值 | `nan_to_num(..., nan=0)` 后分箱 | token=`NA=2`，scalar=0 | 真实 0 与缺失 0 可区分 |
| 分箱拟合 | 单次有上限的抽样池 | 全训练流三遍统计 + 确定性分层 bottom-k reservoir | V2 可复现、路径顺序无关、可审计 |
| 重复分位点 | 用 linspace 补齐到请求箱数 | 合并重复边界，记录实际箱数 | 不制造没有数据支持的伪 bin |
| 分布统计 | 主要保存边界和 fit dates | occupancy、missing、UNK、entropy、mean/std/min/max、sampling | 支持 Loss 归一化与漂移诊断 |
| shard 存储 | 普通整数 token parquet | token `uint8/uint16`，scalar 对称 Q16 `int16` | 降低体积并冻结反量化尺度 |
| shard 合约 | 基础 vocab/schema 约束 | sidecar 绑定 schema、vocab hash、排序、变换和存储 hash | 读取前 fail closed |
| Dataset | `EventWindowDataset`，固定字段顺序 | `EventWindowDatasetV2`，从 FieldSpec 派生布局 | 动态读取 token/scalar/mask |
| 字段融合 | 经典默认 `legacy_sum` | 推荐 `gated_sum`，另有 `scaled_sum/concat_mlp` | 控制字段尺度和单字段依赖 |
| 连续输入 | 无 | `token_embedding + Linear(val, bias=False)` | 离散稳定性与连续精度并存 |
| Transformer 主干 | Decoder-only、RoPE、RMSNorm、SwiGLU | 主干范式不变 | V2 不是换成另一类序列模型 |
| FFN 宽度 | 经典按 `ffn_mult` | 主配置显式 `ffn_hidden` | 精确控制参数量和 active compute |
| 预训练目标 | 6 路等权 CE 求和 | 显式 TargetSpec + mask + entropy normalization + ordinal | 任务难度、适用范围和距离结构显式化 |
| MoE | 不是版本定义；已有 V1 MoE 实验 | 可选 V2 Backbone/Temporal MoE | MoE 与 Token 版本正交 |
| 股日池化 | `flat_v1 / mean` | 跨 chunk 正确 multi-scale | 保留尾盘、时段和近期事件信息 |
| 验证采样 | 旧流程可取前若干 batch | 固定分层 `validation_windows.json` | 架构间比较使用相同窗口 |
| 训练预算 | 历史 `step` 口径可能混合 micro/update | 分开 micro/update/sample/non-pad token | 分布式预算可解释 |
| checkpoint | 旧 checkpoint 元数据较少 | `fm_artifact_version=2.0` 严格冻结全契约 | 禁止 V1/V2 静默混载 |
| 下游 | 历史 mean embedding + legacy Ranker | 严格表征合约 + Ranker artifact v2 代码 | 生产仍只交付 `date,symbol,score` |
| 当前成熟度 | 正式训练和历史产物较完整 | 代码完整、正式 FULL 数据/训练/OOS 待完成 | 不能直接宣称 V2 收益优于 V1 |

## 4. Token：V1 到 V2 的核心变化

### 4.1 V1 Token 结构

V1 不是一个巨大的组合词表。每个事件位置包含 9 个相互独立的字段 token：

| 类型 | 字段 |
|---|---|
| 类别 | `evt_type`、`side`、`session`、`board`、`order_type`、`event_source` |
| 数值分箱 | `price_rel`、`log_volume`、`log_delta_t` |

默认 next-event 目标为：

```text
tok_evt_type
tok_side
tok_session
tok_price_bin
tok_volume_bin
tok_delta_t_bin
```

V1 的正确之处是“一条事件、多字段并行编码”，而不是把全部字段做笛卡尔积。
它的问题主要是缺失语义、连续精度、字段契约和盘口上下文不足。

### 4.2 V2 基础字段

`DEFAULT_FIELD_SPECS_V2` 冻结 6 个字段：

| 逻辑字段 | 类型 | bins | 输入 | 目标 | 输出 |
|---|---|---:|---:|---:|---|
| `evt_type` | categorical | — | 是 | 是 | `tok_evt_type` |
| `side` | categorical | — | 是 | 是 | `tok_side` |
| `session` | categorical | — | 是 | 否 | `tok_session` |
| `price` | ordinal | 32 | 是 | 是 | `tok_price_bin + val_price` |
| `volume` | ordinal | 32 | 是 | 是 | `tok_volume_bin + val_volume` |
| `delta_t` | ordinal | 32 | 是 | 是 | `tok_delta_t_bin + val_delta_t` |

V2 第一阶段主动删除：

- `event_source`：与事件类型高度确定性相关；
- `order_type`：当前 V1 中大量值是规则推断，不是真实交易所语义；
- 逐事件 `board`：静态、低变化，更适合作为数据分层或下游上下文；
- `session` 的预测头：它仍是输入，但不是主 next-event 目标。

### 4.3 FULL V2 盘口字段

`FULL_FIELD_SPECS_V2` 在 6 个基础字段后加入 9 个盘口输入：

| 字段 | 时点 | bins | 是否当前目标 |
|---|---|---:|---:|
| `book_valid_post` | post-event | categorical | 否 |
| `spread_ticks_post` | post-event | 16 | 否 |
| `microprice_delta_ticks_post` | post-event | 21 | 否 |
| `imbalance_l1_post` | post-event | 21 | 否 |
| `imbalance_l5_post` | post-event | 21 | 否 |
| `imbalance_l10_post` | post-event | 21 | 否 |
| `log_bid_depth_l5_post` | post-event | 32 | 否 |
| `log_ask_depth_l5_post` | post-event | 32 | 否 |
| `event_price_distance_ticks_pre` | pre-event | 32 | 否 |

`cn_l2_v2` schema 还增加 `exchange_seqnum` 和 `time_of_day_ms`。它们当前不是
`FULL_FIELD_SPECS_V2` 中的默认 token 输入；前者主要用于顺序审计，后者用于时间/池化语义。

`post_event_state(t)` 可以作为事件 `t` 的表示去预测 `t+1`，不构成未来泄漏；
`event_price_distance_ticks_pre` 必须使用事件发生前 midpoint，避免用本次事件改变后的盘口
解释本次事件价格。

### 4.4 特殊 ID

| 语义 | V1 | V2 | 当前是否实际插入序列 |
|---|---:|---:|---|
| PAD | 0 | 0 | 是，用于 batch padding |
| UNK | 无独立 ID | 1 | 是，类别有值但不在冻结表中 |
| NA | 无独立 ID | 2 | 是，缺失或字段不适用 |
| BOS | 无 | 3 | 仅预留，当前编排未默认插入 |
| EOS | 无 | 4 | 仅预留，当前编排未默认插入 |
| SESSION_BREAK | 无 | 5 | 仅预留，当前编排未默认插入 |
| 首个普通值/bin | 1 | 6 | 是 |

“ID 已冻结”和“token 已插入”是两件事。不能因为 V2 预留了 BOS/EOS/SESSION_BREAK，
就声称模型已经使用了这些边界 token。

### 4.5 连续双通道

V1 数值路径：

```text
raw value → transform → 32-bin token → embedding
```

V2 数值路径：

```text
raw value
  ├─ frozen quantile bins → tok_<field>_bin → embedding
  └─ clip((value - train_mean) / train_std) → val_<field> → Linear(no bias)

field representation = token embedding + scalar projection
```

V2 scalar 缺失位置写 0，但同时令 token=`NA_ID=2`。因此模型能区分：

- `val=0 + 普通 bin token`：数值接近训练均值；
- `val=0 + NA token`：缺失或不适用。

当前 FM Loss 仍预测离散 bin，没有直接回归 `val_*`；scalar 是输入增强，不是新的默认
连续回归目标。

### 4.6 Vocab 拟合

V1：

1. 只在训练 shard 上拟合；
2. 每字段最多收集固定数量样本；
3. 对样本做分位分箱；
4. 重复边界不足时用 linspace 补齐；
5. 保存边界和 fit dates。

V2：

1. Pass 1 遍历完整训练流，统计 count/missing/mean/std/min/max、类别计数和 strata；
2. Pass 2 按 `date × exchange × board × evt_type` 做确定性 bottom-k priority reservoir；
3. Pass 3 在冻结边界上重新遍历完整训练流，计算精确 occupancy；
4. 重复分位点直接合并，`actual_n_bins` 可以小于 `requested_n_bins`；
5. 保存训练熵、缺失率、UNK、normalizer、采样 seed/方法和真实 observed dates；
6. 显式 `fit_dates` 必须与实际读到的日期完全相等。

V2 reservoir 的优先级来自稳定 shard identity、event index、field 和 seed，因此结果不依赖
调用方 path 顺序。它解决的是“样本覆盖与复现”，不是让 validation/test 参与拟合。

### 4.7 存储与 artifact

V2 parquet 使用：

- token vocab size `<=256`：`uint8`；
- token vocab size `<=65536`：`uint16`；
- scalar：对称 Q16 `int16`，读取后解码为 `float32`；
- 每个 shard 配套 `.parquet.contract.json` sidecar。

sidecar 和 checkpoint 至少绑定：schema、vocab SHA-256、字段顺序、事件排序、特征变换、
存储 dtype/scale 和 metadata hash。V1 旧 shard 不能仅补一份 sidecar 就变成 V2；如果底层
排序、参考价或盘口时点不合格，必须从 raw 数据重新回放。

## 5. Loss：三层目标不要混在一起

QuantFM 有三类完全不同的 Loss：

```text
事件级 FM next-event Loss
  +（仅 MoE）Router auxiliary Loss
      ↓ 冻结 FM 并提取 embedding
股日横截面 Ranker Loss
```

下游 Top-K Loss 不替代 FM next-event Loss，也不允许把未来收益梯度反传到 Tokenizer/FM。

### 5.1 FM V1：六路等权 CE

位置 `t` 的 hidden state 预测 `t+1` 六个字段。对字段 `f`：

\[
L_f^{CE}=\operatorname{CE}(\hat y^f_{t+1},y^f_{t+1})
\]

总目标：

\[
L_{V1}=L_{evt}+L_{side}+L_{session}+L_{price}+L_{volume}+L_{delta\_t}
\]

仅用序列 `attention_mask[t] & attention_mask[t+1]` 排除 padding，并以 `PAD_ID=0`
作为 ignore index。六个字段没有显式任务权重，也没有按字段训练熵归一化。

优点：

- 简单、稳定；
- 已有多档真实 checkpoint；
- 便于复现旧结果。

局限：

- session 等低熵任务与 volume 等高熵任务直接相加，Loss 数值不可按难度公平比较；
- 没有独立 NA，无法精确屏蔽不适用目标；
- price/volume/delta_t 是有序桶，但普通 CE 将“错一格”和“错到最远端”同等处理；
- total CE 可能由容易字段改善主导，掩盖关键字段退化。

### 5.2 FM V2：TargetSpec

V2 每个预测头都冻结一份 `TargetSpec`：

```text
name
loss_type: ce | ordinal_ce
weight
train entropy
ordinal_weight / ordinal_start_id
applicable_event_ids
ignore_ids
mask_field
```

V2 没有显式 `loss.targets` 时直接拒绝训练，不会静默退回 V1 等权 CE。

### 5.3 V2 有效目标 mask

字段 `f` 的有效集合为：

\[
M_f=M_t\land M_{t+1}\land(y_f\notin Ignore_f)
\land Applicable_f\land ExplicitMask_f
\]

当前 V2 默认忽略 `PAD=0` 与 `NA=2`。Dataset 还会为目标字段生成
`mask_<target>`。如果一个 batch 中某任务全是 NA 或不适用，代码返回保留计算图的零 Loss，
不会产生 NaN，也不会阻断 backward。

### 5.4 训练熵归一化

V2 vocab 从完整训练流 occupancy 计算字段 unigram entropy：

\[
H_f=-\sum_c p_{f,c}\log p_{f,c}
\]

默认排除会被 applicability mask 忽略的 NA；类别 UNK 是有效预测类，因此计入。单字段主项：

\[
L_f^{norm}=\frac{L_f^{CE}}{\max(H_f,10^{-6})}
\]

直觉上，它衡量“相对该字段自身无条件不确定性”的误差，而不是让类别多、天然高熵的字段
仅凭 CE 尺度支配总 Loss。`H_f` 只能从训练集计算，并随 vocab/checkpoint 冻结。

### 5.5 Ordinal 距离项

对 price/volume/delta_t，先移除前 6 个特殊 ID，得到普通 bin 下标。模型在普通 bin logits
上重新 softmax，并计算期望桶：

\[
\hat b=\sum_{j=0}^{B-1}P(j)j
\]

距离项为：

\[
L_f^{ord}=\operatorname{SmoothL1}
\left(\frac{\hat b}{B-1},\frac{b}{B-1}\right)
\]

CE 仍监督完整分类分布；ordinal 项额外告诉模型桶之间有顺序和距离。它不是把 CE 替换成
单点回归。

### 5.6 V2 FM 总目标和当前权重

\[
L_{V2}=\sum_f w_f\left(
\frac{L_f^{CE}}{H_f}+\alpha_fL_f^{ord}
\right)
\]

| 字段 | 类型 | `w_f` | `alpha_f` |
|---|---|---:|---:|
| `tok_evt_type` | CE | 1.00 | 0 |
| `tok_side` | CE | 1.00 | 0 |
| `tok_price_bin` | ordinal CE | 1.00 | 0.50 |
| `tok_volume_bin` | ordinal CE | 0.50 | 0.25 |
| `tok_delta_t_bin` | ordinal CE | 0.50 | 0.25 |
| `tok_session` | 仅输入 | — | — |
| 9 个盘口字段 | 仅输入 | — | — |

当前没有加入 microprice/mid/OFI/volatility 未来辅助目标，也没有将 T+1 收益放入 FM
预训练。它们仍是候选设计，不属于当前 V2 实现。

### 5.7 为什么 V1/V2 val loss 不能直接横比

V1 total val loss 是 6 个 raw CE 的和；V2 total val loss 是 5 个熵归一化、加权并可能带
ordinal 项的和。目标数、尺度、mask 和权重都不同。

因此：

- V1 的 `5.81` 与 V2 smoke 的 `4.13` 不能解释为 V2 更好；
- 正确比较必须看同一字段的 raw CE、CE/训练熵、accuracy、copy/unigram baseline；
- 最终还要在冻结 embedding 和相同 Ranker/OOS 协议下比较 paired daily IC 与 Top-K 收益。

### 5.8 MoE Router Loss

每个 MoE 层额外计算：

\[
L_{router}=0.01L_{balance}+0.001L_z
\]

其中：

\[
L_{balance}=E\sum_e I_eF_e,
\qquad
L_z=\mathbb E\left[\log\sum_e\exp(z_e)\right]^2
\]

- `I_e` 是平均 soft routing probability；
- `F_e` 是 detach 后的硬路由负载；
- balance loss 防止专家塌缩；
- z-loss 防止 router logits 无限制增大。

FM + MoE 的训练目标为：

\[
L_{FM+MoE}=L_{next-event}+\sum_{l\in MoE\ layers}L_{router}^{(l)}
\]

Router Loss 不是预测质量目标。它只能辅助路由健康，不能替代 per-field CE、下游 IC、
expert fraction、entropy 和 overflow 监控。

### 5.9 下游 Ranker Loss 是另一阶段

当前严格 Ranker artifact v2 代码使用：

\[
L_{ranker}=1.0L_{MultiK\ LambdaNDCG}+0.30L_{global\ IC}+0.05L_{aux\ Huber}
\]

默认 `K=(50,300,350)`，权重 `(0.20,0.60,0.20)`；每天最多采样 8192 pairs，其中
75% 聚焦真实/预测头部和 K 边界，25% 来自全截面。所有 Loss 按交易日独立计算，日期等权。

这与 FM V1/V2 的关系是：

- FM 先训练并冻结；
- Ranker 只接收冻结股日 embedding 与 T 日可用特征；
- T+2 执行收益只做 Ranker 标签；
- 历史本地 Ranker checkpoint 缺少新 objective/training contract，仍是 legacy 产物；
- 新 Ranker Loss 代码已实现，但没有一份已完成、可审计的正式新 Ranker artifact 可证明收益。

## 6. MoE：V1/V2 中到底哪里不同

### 6.1 MoE 不是 V2 的必选项

Dense V2 是正式基线；MoE 是通过 Dense V2 后才考虑的研究扩展。当前公共 `TopKRouter`、
`SparseMoEFeedForward` 和 `TemporalRegimeMoE` 并不依赖 V2 Token，所以可以与 V1 或 V2
artifact 组合。

V1 MoE 与未来 V2 MoE 的核心区别不是 router 算法，而是 router 所在 FM 接收到的
Token、盘口、scalar、主任务 Loss、pooling 和 artifact 契约不同。

### 6.2 两类 MoE

| 项目 | Temporal Regime-MoE | Backbone-MoE |
|---|---|---|
| 放置位置 | 股日/日内聚合之后 | Transformer block 的 FFN 位置 |
| 路由单位 | 股日或时间摘要 | 每个有效事件 token |
| Router 输入 | 显式、同一时点可用的 regime 特征 | 当前层 hidden state |
| 默认 routed experts | 4 | 4 |
| shared expert | 1 | 1 |
| 默认 Top-K | Top-2 | Top-1 |
| 是否复用 Dense FM | 是 | 否，需要重训 |
| 成本 | 较低 | 高，增加总参数和 dispatch 成本 |
| 主要风险 | regime 泄漏、PIT join、样本不足 | collapse、overflow、batch 依赖、FSDP/吞吐 |
| 当前状态 | 独立模块，未接标准训练/评分 | 已有 V1 完整训练；V2 正式训练未开始 |

只有 Temporal Router 明确读取 regime feature。Backbone Router 读取 token hidden，学到的
更可能是事件类型、流动性或 session 分工，不能直接命名为“牛市/熊市专家”。

### 6.3 公共 Top-K Router

\[
z=f_{router}(x)/T,\qquad p=softmax(z)
\]

选择概率最高的 K 个专家，并在 Top-K 内重新归一化：

\[
w_i=\frac{p_i}{\sum_{j\in TopK}p_j}
\]

Router logits 和 softmax 强制 FP32，减少 bf16/fp16 下的路由抖动。

- Backbone Router：单层无 bias `Linear(d_model, n_experts)`；
- Temporal Router：`LayerNorm → Linear → SiLU → Linear`；
- 当前 `temperature=1.0`。

### 6.4 Backbone-MoE 结构

只替换指定 Transformer 层的 Dense SwiGLU FFN，Attention、RoPE、RMSNorm、残差路径不变：

```text
active token hidden
  ├─ shared SwiGLU expert：所有有效 token 都执行
  └─ Top-K Router
       └─ routed expert 0..3：只执行被选中的 expert

output = shared(active) + weighted routed(active)
```

当前冻结配置：

```yaml
layer_indices: [14, 15, 16, 17]
n_routed_experts: 4
top_k: 1
shared_expert_hidden: 1024
routed_expert_hidden: 1792
capacity_factor: 1.25
load_balance_weight: 0.01
router_z_loss_weight: 0.001
```

底部 14 层仍是 Dense，顶部 4 层是 MoE。每个 token 激活的 expert hidden 总宽度为
`1024 + 1792 = 2816`，与 Dense230M 的 `ffn_hidden=2816` 对齐 active hidden 预算；
MoE 的总参数仍更大。

### 6.5 Capacity 与 overflow

对 N 个有效 token、K 个路由选择、E 个专家：

\[
C=\left\lceil capacity\_factor\frac{NK}{E}\right\rceil
\]

- PAD 不进入 Router、容量或负载统计；
- 训练时单专家超过容量，只保留 router weight 最大的 C 个 assignment；
- 被裁剪 assignment 没有 routed 输出，但仍有 shared expert 保底；
- 评估/推理时不裁剪，`overflow_rate=0`，保证结果不随 batch size 改变。

这会产生明确的 train/eval 差异：训练期 assignment 在整个 batch 的有效 token 之间竞争容量，
可能形成 batch 依赖。没有训练期 overflow telemetry，就不能仅凭验证 Loss 判定 MoE 健康。

### 6.6 Temporal Regime-MoE

Temporal 路径位于 `IntradayAggregator.full_day_summary` 后：

\[
h'=h+E_{shared}(h)+\sum_{e\in TopK}w_eE_e(h)
\]

默认 4 routed experts、Top-2、expert hidden 256、router hidden 128。Router feature 只能来自
评分时点已知数据，例如截至当时的波动、宽度、成交额、价差、市场/行业状态。

当前 `RegimeFeatureSpec.availability_lag` 和 normalizer `fit_end` 只是审计元数据；代码不会
自动替调用方完成 lag、PIT as-of join 或训练日期过滤。因此该模块具备因果 API，不等于
上游数据天然无泄漏。

### 6.7 MoE 必须监控什么

| 类别 | 必要指标 |
|---|---|
| 主任务 | total loss、per-field raw/normalized CE、ordinal |
| Router | expert fraction、normalized entropy、mean top-1 probability |
| Capacity | overflow、accepted assignments、capacity |
| 专家差异 | 输出余弦相似度、专家梯度范数 |
| 性能 | non-pad tokens/s、dispatch/combine、峰值显存 |
| 稳定性 | 按日期、波动、流动性、事件类型的专家占比 |

建议告警线是单专家长期 `>80%`、任一专家长期 `<5%`、overflow 长期 `>5%`。这些只是
应先在 warmup 冻结的研究门槛，不是当前已经通过的验收结果。

当前训练 loop 只自动写合计 `train/moe_aux`，还没有把逐层 expert fraction、entropy 和
overflow 完整持久化。因此即便存在 final checkpoint，也仍缺路由健康度证据。

### 6.8 当前本地 V1 Dense/MoE 对照

2026-07-31 直接检查本地 final checkpoint：

| 项目 | Dense230M V1 | Backbone-MoE V1 |
|---|---:|---:|
| 参数量（文档实测） | 231.52M | 297.59M |
| 数据/vocab | cont60 V1 | cont60 V1 |
| 主 Loss | 六路等权 CE | 六路等权 CE |
| updates | 50,000 | 50,000 |
| non-pad tokens | 12,875,096,787 | 12,875,096,787 |
| validation plan SHA-256 | `ef89b68c...0bcaaad` | 相同 |
| best val loss | 5.81305394 | 5.81594505 |
| final/final_resume | 有 | 有 |

MoE 比 Dense 高 `0.00289112` raw val loss，约 0.05%。这只说明在当前同数据、同验证窗口、
同训练预算的 V1 next-event 指标上没有显示出优势；差值很小，而且缺少逐层路由 telemetry、
吞吐和严格下游 OOS，不能据此得出最终投资效果结论。

这份本地证据也说明 2026-07-30 文档中“MoE 停在 38,375、没有 final”的现场记录已过期。

## 7. 模型、训练和表征的其他差异

### 7.1 字段融合

| 方法 | 语义 | 典型用途 |
|---|---|---|
| `legacy_sum` | 所有字段 `d_model` embedding 直接相加 | 旧 V1 checkpoint 兼容 |
| `scaled_sum` | field dropout 后按权重 L2 范数缩放再求和 | 控制字段数带来的尺度变化 |
| `gated_sum` | 每字段可学习 sigmoid gate + dropout + RMSNorm | 当前 V2 推荐，也用于新 V1 compatibility 实验 |
| `concat_mlp` | 每字段低维表示拼接，经两层 MLP 投到 `d_model` | 消融候选 |

`field_dropout` 是一次 forward 共用的字段 mask，并保证至少保留一个字段。它不等于 PAD/NA，
也不改变 token 语义。

### 7.2 Transformer 主干和性能语义

V1/V2 共用 Decoder-only causal Transformer：RoPE、pre-norm RMSNorm、SDPA attention、
SwiGLU。V2 分支新增或强化的以下能力也能被 V1 compatibility 配置使用：

- 显式 `ffn_hidden`；
- RoPE cache；
- 无 padding 时 `attn_mask=None, is_causal=True` 快路径；
- shard-aware sampler；
- pinned memory、non-blocking copy、persistent workers/prefetch；
- micro/update/sample/non-pad token 分开计数；
- inference checkpoint 与 resumable checkpoint 分离。

这些是分支级工程改进，不应单独作为“使用了 V2 Token”的证据。

### 7.3 Pooling

V1 基线通常使用 `flat_v1 / mean`，把全日事件 hidden 做一个均值。V2 正式配置使用
跨 chunk 正确的多尺度输出：

```text
mean_all
last_256
continuous_pm
close_30m
```

完整池化实现还支持 `last_1024/open_call/continuous_am/close_call`。新实现会跨所有 chunk
维护严格的全日和尾部统计，不会先对各 chunk 等权平均而让短尾 chunk 获得过大权重。

V2 smoke 使用的是旧 `hierarchical_v1` 多尺度布局；正式配置使用显式有序输出的
`hierarchical_selected_v2`。二者 embedding 维度和契约不能混用。

### 7.4 验证与训练预算

V2 配置使用冻结的 `validation_windows.json`，按
`date × exchange × board × liquidity × activity` 近似分层，并保存 manifest fingerprint、
window 参数和 shard hash。数据或窗口参数变化时 fail fast。

训练状态显式区分：

```text
micro_step
update_step
samples_seen
non_pad_tokens_seen
best_val / best_update_step
```

学习率、日志、验证和 checkpoint 由成功的 `update_step` 驱动。fp16 overflow 跳过 optimizer
step 时不增加 update/sample/token。历史 V1 “40k steps”不一定等于 40k optimizer updates，
比较训练预算时必须先核对 checkpoint 中的计数器。

### 7.5 Checkpoint 合约

V1：

```text
schema_version=cn_l2_v1
vocab_version=1.0
fm_artifact_version=1.0
```

V2 还严格冻结并核对：

```text
fm_artifact_version=2.0
schema_version / vocab_version / vocab_sha256
有序 FieldSpec
input_fields / target_fields
continuous normalizers
TargetSpec / Loss 配置
field fusion / scalar mapping / ffn_hidden
book state timing
context / pooling version / outputs / stride
event ordering / feature transform
Backbone-MoE 配置
```

加载 V2 checkpoint 必须提供原始 `vocab_v2.json`。只复制模型权重、换一份字段顺序相似的
vocab，或者用 V1 token 加载 V2 checkpoint，都应该直接失败。

## 8. 当前状态与能下什么结论

| 对象 | 当前状态 | 可以声称 | 不能声称 |
|---|---|---|---|
| V1 Pilot/Medium/302M/Dense230M | 有历史正式 checkpoint | V1 训练链已跑通 | 代表 V2 数据或 Loss |
| Backbone-MoE V1 | 已完成 50k，本地有 final | V1 MoE 训练预算完成 | 路由健康、吞吐或 OOS 已胜出 |
| V2 25M smoke | 5 updates，有 final | V2 base Token/Loss 工程可运行 | 正式 25M、FULL 盘口或收益结论 |
| V2 25M/100M/230M | 配置就绪 | 可以开始受控实验 | 已训练或已优于 V1 |
| V2 Backbone-MoE | 配置/日期计划就绪 | 工程候选存在 | 正式训练、路由或 OOS 已验收 |
| Temporal Regime-MoE | 独立模块和部分 artifact | API 与单测存在 | 已接生产评分或已有正式 checkpoint |
| Ranker artifact v2 | 代码和严格合约已实现 | 新 Top-K 训练路径可执行 | 已有正式新 Ranker 结果 |

当前最准确的总判断是：

> V2 在数据语义、Token 表达、Loss 可解释性和 artifact 安全性上显著更完整；
> 这些是工程与研究设计优势，不是已经证明的收益优势。正式结论仍需 FULL V2 数据、
> Dense 单因素消融、多 seed、固定验证、相同 Ranker 和新的 untouched OOS。

## 9. 推荐的严格对照顺序

为了知道收益来自哪里，不要一次同时切 Token、Book、Loss、Fusion 和 MoE。推荐顺序：

1. 固定日期、股票池、context、有效 token、validation windows 和 seeds；
2. V1 fields + V1 CE，建立可复现基线；
3. 只换 V2 base fields/特殊 ID；
4. 只增加 token+scalar；
5. 只增加 entropy normalization；
6. 再增加 ordinal 项；
7. 再增加 FULL 因果盘口字段；
8. 再比较 `legacy_sum/scaled_sum/gated_sum`；
9. Dense winner 晋级 100M/230M；
10. 冻结同一个 FM/embedding 后先测低成本 Temporal Regime-MoE；
11. 最后在相同 Token、Loss、预算和验证窗口下比较 Dense 与 Backbone-MoE。

比较报告至少同时给出：

- per-field raw CE、normalized CE、ordinal、accuracy、valid count；
- unigram/copy baseline；
- 参数量、active FFN hidden、non-pad tokens/s、显存；
- MoE expert fraction、entropy、overflow；
- paired daily IC、RankIC、Top-K 扣成本收益、换手和 MDD；
- 3–5 seeds 与最终 untouched OOS。
