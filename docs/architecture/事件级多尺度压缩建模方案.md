# QuantFM 事件级多尺度压缩建模方案

> 文档状态：架构候选方案，未实施  
> 整理日期：2026-08-06  
> 适用范围：QuantFM V2 逐笔事件、因果订单簿、日内表征与股日选股信号

## 1. 背景与问题

QuantFM V2 使用逐笔委托、撤单和成交事件重建订单簿，并为每个事件生成因果的盘口状态。这一粒度有利于学习撤单、队列变化、主动买卖、流动性冲击和盘口恢复等微观结构，但也导致三类问题：

1. 逐事件回放和盘口快照使清洗时间显著增加；
2. 全市场多日事件数量巨大，token 存储和数据加载成本过高；
3. 大型 Transformer 将每个事件都作为全局 token，大量计算消耗在高度重复的局部变化上。

核心判断是：

- **订单簿重建必须保留事件级粒度**，否则无法可靠复原撤单、成交和队列变化；
- **模型输入不必坚持一个事件对应一个全局 token**；
- 最合理的方向是“事件级重建、局部序列学习、多尺度压缩、长周期建模”。

## 2. 方案目标

本方案不直接删除或降采样原始事件，而是将事件级市场表征分成局部和全局两层：

1. 局部编码器在小窗口内学习微观事件顺序；
2. 每个局部窗口压缩为一个 `block token`；
3. 全局日内模型只处理压缩后的 block 序列；
4. 在不破坏因果性和订单簿语义的前提下，降低存储、训练和推理成本；
5. 使局部表征可被不同全局模型和下游实验重复使用。

本方案的目标不是用简单 K 线代替逐笔数据，而是将高成本的事件级建模限制在局部范围，再将已经学习的微观信息交给长序列模型。

## 3. 总体架构

```text
原始逐笔委托 / 成交
  ↓
交易所时间 + sequence 因果排序
  ↓
事件级订单簿精确回放
  ↓
cn_l2_v2 event + compact post-event book state
  ↓
Tokenizer V2（字段 token + scalar）
  ↓
局部事件编码器（最多 256 events）
  ↓
BLOCK_END hidden + 显式订单流统计 + 期末盘口
  ↓
block token sequence
  ↓
全局日内 Transformer / GRU
  ↓
全日 / 尾盘 / 趋势 / 活跃度多尺度表征
  ↓
横截面 Ranker
  ↓
date, symbol, score
```

## 4. Micro-block 划分规则

### 4.1 第一版推荐规则

从某只股票某个 session 的第一个有效事件开始，按交易所顺序向后累积。满足以下任一条件时结束当前 block：

- 累积到 256 个事件；
- block 从首个事件起已持续 30 秒；
- 遇到 session 切换；
- 遇到股票日末尾。

该规则同时照顾两类标的：

- 高活跃股票由事件数上限控制，避免局部序列过长；
- 低活跃股票由时间上限控制，避免一个 block 跨越过长的市场时间。

### 4.2 因果性要求

- block 边界只能依赖当前及历史事件；
- 每个事件必须且只能属于一个 block；
- block 不得跨越 `symbol/date/session`；
- 不得用全日事件数、未来活跃度或未来波动来决定当前 block 边界；
- 变更未来事件时，已结束 block 的边界和内容必须保持不变。

### 4.3 暂不纳入第一版的规则

第一版不建议因“大额成交”、“spread 跳变”或“imbalance 翻转”动态插入额外事件 token。这些信息应先以 block 内极值、计数和状态标记保留。

只有在基础 block 方案存在明确的稀有事件信息丢失时，才进入“关键事件 residual token”的后续消融。

## 5. Block 数据契约

### 5.1 索引与血缘字段

每个 block 至少保存：

```text
schema_version
block_version
symbol
security_id
date
exchange
session
block_id
start_event_idx
end_event_idx
start_int_time
end_int_time
event_count
duration_ms
```

block artifact 还必须绑定：

- 原始 V2 manifest 及其 hash；
- `vocab_v2.json` hash；
- 事件排序版本；
- 订单簿状态时点语义；
- block 边界配置和版本；
- 局部编码器 checkpoint hash；
- 显式统计字段顺序与标准化参数；
- train/validation/test 日期划分。

本方案不应静默复用 `cn_l2_v2` 的文件名作为 block schema。实施时应创建独立、显式版本化的 block artifact 契约。

### 5.2 订单流显式统计

每个 block 推荐保留：

- `ADD/CANCEL/TRADE` 数量及占比；
- 买卖方向的委托量、撤单量和成交量；
- 主动买/主动卖成交量；
- signed order-flow imbalance；
- 最大单笔委托、撤单和成交；
- 成交金额与笔数；
- `delta_t` 均值、最大值和分位数；
- block 事件密度。

连续特征只能用训练日期拟合的 normalizer 进行标准化。

### 5.3 盘口与价格特征

每个 block 应同时保留“期初、期末、变化量和极值”，避免只做均值导致冲击与恢复过程被抹平。

推荐字段包括：

- block 期初/期末 bid1、ask1、midpoint 和 microprice；
- 期初/期末 spread；
- L1/L5/L10 imbalance 及其变化；
- L5/L10 买卖深度及其变化；
- block 内 spread 最大值和最小值；
- midpoint 变化和区间波动；
- 单边盘口、流动性枯竭和涨跌停状态标记；
- block 内最大瞬时价格冲击。

## 6. 局部事件编码器

### 6.1 推荐初始配置

```yaml
local_encoder:
  context: 256
  d_model: 256  # 384 作为放大候选
  n_layers: 4   # 6 作为放大候选
  n_heads: 8
  causal: true
  field_fusion: gated_sum
```

局部编码器继续使用 V2 的：

- 冻结 `FieldSpec`；
- token + normalized scalar 双通道；
- 事件级因果顺序；
- next-event 多任务 Loss；
- NA/适用性 mask；
- 训练集熵归一化和 ordinal 距离约束。

第一版不建议将 MoE 加入局部编码器，以免将“压缩是否有效”与“路由是否有效”混为同一个实验问题。

### 6.2 Block summary token

在 block 最后一个事件之后追加 `BLOCK_END` token。对因果 Transformer 而言，该位置可以 attention 到 block 内所有历史事件，但不会看到下一个 block。

`BLOCK_END hidden` 用作 learned summary，与显式订单流和期末盘口统计融合：

```text
block_token = projection(
    block_end_hidden
    || normalized_flow_statistics
    || ending_book_state
    || time_and_session_features
)
```

显式统计和 learned summary 不应二选一：

- learned summary 学习局部事件顺序和非线性模式；
- 显式统计确保稀有冲击、流量总量和期末盘口不因 pooling 而消失。

## 7. 全局日内模型

### 7.1 输入

全局日内模型只接收 block token，并额外融合：

- block 结束的真实日内时间；
- session id；
- block 持续时间；
- event count 的标准化或分箱表示；
- block 有效性 mask。

不得使用“block 在当日总 block 数中的百分位”作为位置编码，否则早期 block 会间接获得未来的全日活跃度。

### 7.2 初始候选

第一轮建议同时保留两个候选：

1. 复用已有的因果 `IntradayAggregator` GRU，用于快速验证学习式日内聚合是否有价值；
2. 使用 4–8 层的小型因果 Transformer，用于正式学习较长的 block 依赖。

只有在 Dense 全局模型已证明有效后，才应开展 Regime/Backbone MoE 消融。

### 7.3 自监督目标

局部编码器继续预测下一个事件。全局日内模型预测下一个 block 的：

- event-type 分布；
- signed OFI 分箱；
- 委托、撤单和成交量分箱；
- midpoint return 分箱；
- 期末 spread 与 imbalance；
- block 内 realized volatility；
- block duration 和活跃度。

这些目标属于 next-block 自监督学习，可以使用下一个 block 作为标签，但输入仍必须只包含当前及历史 block。

未来收益标签仍然只进入下游 Ranker，不得通过局部或全局预训练目标回传到 tokenizer/FM。

## 8. 股日表征与下游链路

全局日内模型可输出四路股日表征：

```text
full_day_summary
close_summary
intraday_trend_summary
activity_summary
```

固定池化对照继续使用已有 `hierarchical_selected_v2` 布局：

```text
mean_all
last_256
continuous_pm
close_30m
```

新旧表征必须使用独立的 pooling/aggregator 版本和 checkpoint 契约，不得因输出维度相同而静默混用。

下游仍保持两阶段边界：

```text
冻结局部编码器 + 冻结全局日内模型
  ↓
生成股日 embedding
  ↓
横截面 Ranker / Top-K Loss
  ↓
严格 OOS score 和扣成本回测
```

## 9. 训练与产物生成流程

### 阶段 A：局部事件编码器

- 在冻结的训练日期上拟合 V2 vocab 和 normalizer；
- 使用最多 256 事件的 block 训练小型 next-event 模型；
- 固定验证窗口，记录 per-field NLL、顺序距离、吞吐和显存；
- 冻结获胜的局部 checkpoint。

### 阶段 B：生成 block artifact

- 使用冻结局部编码器对每个 block 前向一次；
- 将 `BLOCK_END hidden` 与显式统计一起写入 block shard；
- 记录 block 边界、原始事件范围、行数和 hash；
- 生成 block manifest 和覆盖率审计；
- 局部 embedding 只生成一次，供多个全局模型实验重用。

### 阶段 C：全局日内预训练

- 使用压缩后的 block 序列训练 next-block 模型；
- 先训练 Dense GRU/Transformer；
- 在固定验证集上选定聚合与全局架构；
- 只有 Dense 候选通过后才开展 MoE 实验。

### 阶段 D：股日 embedding 与 Ranker

- 冻结局部和全局 FM；
- 为训练、验证和 OOS 日期生成同契约的股日 embedding；
- 使用现有 Ranker 与 Top-K Loss 训练下游信号；
- 执行 paired daily IC、Top-K 扣成本回测和严格 OOS 验收。

## 10. 实验矩阵

| 实验 | 输入表示 | 局部模型 | 全局模型 | 主要目的 |
|---|---|---|---|---|
| E0 | 完整事件级 V2 | 无分层 | 当前事件 Transformer | 基准 |
| E1 | 当前事件 hidden/chunk summary | 当前 FM | `IntradayAggregator` | 验证 learned 日内聚合，不解决事件计算量 |
| E2 | 纯显式 block statistics | 无 | GRU/小型 Transformer | 验证最大压缩下限 |
| E3 | `BLOCK_END hidden` + block statistics | 小型事件 Transformer | GRU/小型 Transformer | 推荐主候选 |

第一轮只固定一套 block 规则（256 events / 30 seconds / session boundary）完成 E0–E3，避免同时搜索过多 block 大小、模型宽度和 pooling 方法。

E3 通过后，第二轮再做小规模边界消融：

- 128 vs 256 events；
- 10 vs 30 seconds；
- 无 shock boundary vs 因果 shock boundary；
- GRU vs 小型 Transformer。

## 11. 验收标准

### 11.1 数据正确性硬门槛

- 事件数覆盖率必须为 100%；
- 每个事件只能出现一次；
- block 不跨 `symbol/date/session`；
- block 末尾盘口必须与原始事件回放一致；
- block 统计聚合回股票日后，事件数、成交量、撤单量等必须与原始数据一致；
- prefix-causality 测试必须通过；
- 任何缺失 artifact hash、边界配置或局部 checkpoint 的 block 数据必须 fail closed。

### 11.2 效率目标

第一轮建议预先冻结以下目标：

- block 总行数至少比事件数降低 32 倍，目标为 64–256 倍；
- block artifact 存储低于逐事件 token artifact 的 10%；
- 全局模型训练墙钟时间至少降低 5 倍；
- 局部 block embedding 可被多个全局实验重复使用，无需重复读取和编码全部事件；
- 报告分开记录一次性局部编码成本和可重复的全局训练成本。

这些是候选目标，不应在实测前宣称已达成。

### 11.3 表征与下游质量

至少比较：

- local next-event per-field NLL/熵归一化 NLL；
- global next-block 分类和回归指标；
- paired daily RankIC 与 ICIR；
- Top-K 扣成本收益、换手、回撤和胜率；
- 大额成交、spread 跳变、强 imbalance、尾盘和低流动性子样本；
- 不同活跃度、板块和交易所分层表现；
- 至少 3 个 seed 的均值和离散程度。

压缩方案不能只因为吞吐更高就晋级。E3 必须在冻结验证集上相对 E0 达到预先声明的非劣容忍区间，并且 Top-K 扣成本表现不得出现实质性恶化。非劣界限应在查看新实验结果之前冻结。

## 12. 与清洗性能的边界

本方案主要解决：

- 逐事件 token 的长期存储；
- 大型 Transformer 逐事件训练成本；
- 股票日内超长序列的上下文限制；
- 多个全局架构实验反复编码原始事件的浪费。

它不会自动取消事件级订单簿回放。为了保证 V2 盘口正确性，原始清洗仍需要按交易所顺序处理所有事件。

清洗性能应作为独立工作线：

1. 增量维护每个价位的活动挂单总量，避免每个事件重新遍历前十档的所有订单；
2. 用预分配的类型化数组直接收集盘口特征，避免整只股票缓存 Python transition 对象；
3. 在回放时同步累积 block 显式统计，避免事后再扫描一遍事件；
4. 在产物契约验收通过后，只长期保留训练必需的 block artifact、manifest 和审计证据，原始数据由上游 MinIO 和确定性流程保证可重建。

清洗优化和表征压缩可以并行推进，但必须分开测量，不得将“block 数量降低”宣称为“订单簿回放已加速”。

## 13. 实施顺序

### Phase 0：固定基线与证据

- 选择少量冻结日期和股票池；
- 固定 E0 的数据、模型、pooling 和 Ranker 契约；
- 记录事件数、存储、清洗、tokenize、GPU 训练墙钟与下游指标；
- 预先声明非劣界限。

### Phase 1：确定性 block 对照

- 先实验 E2，不引入局部 learned summary；
- 验证 block 边界、数据正确性、压缩率和显式统计的信息下限；
- 确认下游链路可完整运行。

### Phase 2：局部编码器与 E3

- 训练小型局部编码器；
- 生成冻结 block embedding；
- 完成 E3 的 Dense GRU/小型 Transformer 训练；
- 对照 E0/E1/E2 进行效率和下游质量验收。

### Phase 3：小规模消融

- 仅对 E3 附近的 block 大小、时间上限和全局架构做消融；
- 检查关键事件信息是否被压缩；
- 必要时才加入因果 shock boundary 或 residual token。

### Phase 4：放大与严格 OOS

- 只放大通过非劣与效率门槛的 Dense E3 候选；
- 冻结 block、local/global checkpoint、pooling、Ranker 和交易口径；
- 在新的 untouched OOS 日期上完成最终验收；
- 不得将已用于架构设计的 2026 研究窗口重新声称为 untouched OOS。

## 14. 主要风险与缓解措施

### 14.1 稀有冲击被平均

**风险**：大额成交、瞬时流动性枯竭或快速恢复被均值池化稀释。

**缓解**：保留期初/期末/变化/极值，加入最大冲击和状态跳变计数，并使用 `BLOCK_END` learned summary。

### 14.2 固定事件窗口丢失真实时间

**风险**：同样 256 个事件在高活跃股票中可能仅持续毫秒，在低活跃股票中可能持续数分钟。

**缓解**：使用“事件数 + 真实时间 + session”混合边界，并显式输入 duration/time/session。

### 14.3 局部编码器训练仍需要大量事件

**风险**：第一次训练和生成 block embedding 时仍需读取全部逐事件数据。

**缓解**：局部模型使用更小的宽度和 context，block embedding 只生成一次，之后的全局架构、pooling 和 Ranker 实验重用该产物。

### 14.4 新旧 artifact 静默混用

**风险**：将 block token 当作旧 V2 event token 读取，或将不同局部编码器产生的 block embedding 混在同一 manifest。

**缓解**：使用独立 schema/block/checkpoint 版本，强制 hash 和字段顺序校验，不按文件名或输出维度推断契约。

## 15. 推荐结论

推荐的主候选为 E3：

> 保留事件级订单簿重建，使用小型局部编码器学习最多 256 个事件内的微观结构，将 `BLOCK_END hidden`、订单流统计和期末盘口融合为 block token，再由轻量全局日内模型处理长周期依赖。

该方案在三个目标之间取得较好平衡：

- 不牺牲订单簿回放和局部事件顺序；
- 大幅降低全局序列长度和重复训练成本；
- 保留显式、可审计的订单流和盘口信息，不将全部信息压缩责任交给单一 pooling 向量。

正式实施时应先完成 E0/E1/E2/E3 的小规模配对实验，再决定是否放大到完整 V2 训练与新 untouched OOS 验收。
