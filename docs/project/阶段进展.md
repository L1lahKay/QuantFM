## 二、MinIO 读写 Infra（做了什么）

### 2.1 解决的核心问题

前期阻塞主要来自环境与路径，而非模型本身：

- 示例地址 / 示例 bucket 与机房实际不一致
- 读端与写端端口、权限分离，需独立配置
- 原始数据体量大（约 **4 TiB**），不能整盘落地

因此本阶段重点不是「再写一个清洗脚本」，而是**把读写固化成可运维基础设施**。

### 2.2 已落地能力

```text
【读】机房 MinIO :9000 / zeus-cn-quote
        原始 L2（成交 + 委托）
              │
              ▼  Polars 流式读取 + 订单簿重建
        本地 transient 加工
        （events → tokens → vocab / manifest）
              │
              ▼
【写】机房 MinIO :9100 / model-cache
        fm-pretrain/khalil/{规模标签}/
```


| 能力项     | 说明                                    |
| ------- | ------------------------------------- |
| 读写分离    | 读 raw @ `:9000`；写 tokens/产物 @ `:9100` |
| 连通自检    | 一键检查读写 endpoint 是否可达                  |
| 上传 / 下载 | 训练产物可备份到 MinIO，也可按需拉回本机再训             |
| 一键流水线   | 支持「只做数据」或「数据 + 多卡训练」两种模式              |
| 磁盘策略    | 按日处理、本地临时落盘，避免全量原始数据占满机器              |
| 断点续跑    | 日期 `.done` / `.clean_done`；标的级跳过已有 `events.parquet`；events/tokens 文件级跳过 |
| 并行清洗    | `CLEAN_WORKERS` 多进程按标的并行订单簿重建 |
| **高性能清洗** | `--fast-clean`：每日**单次读取** MinIO + SZ/SH 同池 + 本地 raw 缓存续跑 + 列投影（读取 4 次 → 1 次） |
| 并行规范化  | `CANON_WORKERS` 多进程写 canonical events 分片 |
| 按日 tokenize | reuse-vocab 场景下用**独立子进程**逐日 tokenize（避开 clean 后 spawn 池 fork 死锁）并即时删 events 控盘 |
| 进度查询    | `check_pipeline_progress`：完成天数、当日阶段、ETA；`watch_oos2026_live.sh` 实时看板 |
| 看门狗    | `watchdog_oos2026.sh`：进程死亡自动 `--resume` 续跑；卡死阈值 2h（只在真死时重启，杜绝误杀） |
| 训练续训    | checkpoint 含模型 + optimizer + scaler + step；`--resume auto` |




### 2.3 对业务 / 工程的价值

1. **可复现**：任何人配置密钥后，可用同一套命令复现数据制作过程
2. **可扩展**：从 5 日试跑放大到 60 日全市场，只改模式参数，不改架构
3. **可运维**：读写健康检查、产物路径规范、本地与 MinIO 双存策略清晰

## 七、2026 时序 OOS 研究信号 + 高性能清洗

### 7.1 为什么要 2026 数据

300M FM 的 22 个预训练日**撒满整个 2025 年**（最后一天 `2025-12-31`）。要得到「完全晚于训练数据」的样本外（OOS）信号，只能用 **2026 年**——2025 年内任何窗口都与预训练期重叠，存在表征层「软泄漏」。

零泄漏链路：`FM(best.pt, ≤2025)` + `冻结 vocab(2025)` + `Ranker(2025 训练)` → 对 **2026** embedding 前向出 `score`。三者在首次生成时都没见过 2026 表征与标签，因此它是相对 V1 训练链的时序 OOS。但该 60 日现已被用于诊断和设计 V2，后续只能称为 **architecture-validation 窗口**，不得再作为 V2 最终 untouched OOS。

### 7.2 流动股池（可行性 + 成本）

全市场 5105 只 × 60 连续日的清洗（每日下载 ~2.8 亿行 + 全市场订单簿重建）约需 30–40h 且磁盘吃紧。改用**流动 top-1000 股池**（按 day-1/2 的 L2 token 文件大小排序，SZ 625 + SH 375，覆盖 ~55% 全市场活跃度），清洗提速数倍、磁盘可控，截面仍足够宽、RankIC 依然可信。

- 股池：`quant_fm/data/oos2026_liquid_{sz,sh}.txt`
- 交易日：`quant_fm/data/oos2026_dates.txt`（61 天：60 信号 + 1 末日，仅满足旧的一期 fwd return；严格 `vwap_t1_vwap_t2` 需另提供覆盖最后 T+2 的完整日历）
- panel（次日收益标签）已过滤到同 1000 只，保证 60 天截面一致

### 7.3 关键代码 / 脚本

| 文件 | 作用 |

| `quant_fm/lob_rebuild/clean_day_fast.py` | 高性能清洗（单次读 + 双市场同池 + 本地缓存 + 列投影），见 [阶段 2 文档](../pipeline/02_order_book_rebuild.md) |

### 7.4 产出

`quant_fm/runs/oos2026/delivery_oos/`：
- `scores/oos.parquet` —— `date, symbol, score`（2026 全部信号日、每股每日）
- `oos_metrics.json` —— 2026 RankIC / ICIR / 随机基线（V1 时序 OOS 研究记录；对 V2 只是架构验证）

**增量交付**（`run_oos2026_incremental.sh`）：上面的 `delivery_oos/` 会在累计已抽 ≥ `MIN_DAYS`（默认 15）个交易日后**先出第一版**，此后每有新天完成 tokenize 就**覆盖更新**，直到 60 个信号日全部补齐。这样 score 的首次产出时间从「全部跑完」提前到「~1/4 跑完」。累积 embedding 存于 `embeddings/incr/oos_all.parquet`，账本 `embeddings/incr/embedded_dates.txt`（已抽天，绝不重抽）。

> 说明：`2026-01-05/06` 是选流动股池用的**全市场**样本（各 ~5065 分片），`01-07` 起为 liquid ~1000；打分与 liquid panel 内连接，最终打分股池恒为 liquid∩当日可得，跨天一致。

### 7.5 P0-2 跨日并行清洗（实测 2.13× 提速）

各交易日的 `clean/<date>`、`raw_cache/<date>`、`data/.done/<date>`、
`tokens/<market>/<symbol>/<date>.parquet` 全部按 `<date>` 分文件 → **不同日期天然不冲突**，
故无需改 `run_medium` 核心逻辑，只要把日期切成 `NGROUPS` 份、并发跑多个 `run_medium --resume`。

**64 核基准测试**（liquid 1000 只/天，无其他负载）：

| 架构 | 处理量 | 耗时 | 吞吐 |
|------|-------|------|------|
| 旧（单进程，`CLEAN_WORKERS=32`） | 1 天 | 470s | 7.7 天/时 |
| 新（`NGROUPS=2`，各 `CLEAN_WORKERS=30`） | 2 天 | 441s | 16.3 天/时 |

**加速比 ≈ 2.13×**：2 天并发（441s）比旧架构单天（470s）还快——一天的 MinIO 读（I/O）
与另一天的订单簿回放（CPU）相互重叠，且用满 60 核（旧架构只用 32、留一半空闲）。
核数预算：`NGROUPS × CLEAN_WORKERS ≤ nproc`（64 核建议 2×30）。

配套改动：`run_medium` 新增 `--skip-manifest`（并行组跳过收尾 manifest，由驱动统一建一次）；
并修复收尾 leftover-tokenize 清扫**只扫本组日期**（否则多组共享 `events/` 会撞上别组正在写/删的分片）。

> 两处测试期发现并修复的坑：① `GROUPS` 是 bash 保留只读变量（用户 GID 数组），
> 误用会取到 GID（几百）而启动海量进程 → 改名 `NGROUPS` 且加 1..16 防呆校验；
> ② 跨组 tokenize 竞态（见上）。

### 7.6 复盘：为什么一度空转 12h（经验教训）

1. **看门狗误杀**：清洗订单簿重建阶段本就静默 30–40 分钟，旧阈值 30 分钟把健康进程当卡死反复重启 → 每次重启重下 2.8 亿行 → 恶性循环。**已修**：阈值提到 2h，原则改为「只在进程真死时重启」。
2. **spawn 池 fork 死锁**：clean 后残留上百线程/上百 GB 内存的进程再开 `ProcessPoolExecutor(spawn)`，fork+exec 瞬间被拖死。**已修**：每日 tokenize 改独立子进程（`tokenize_dir.py`）。
3. **重复 IO / 无缓存**：即 `--fast-clean` 解决的双读 + 重启重下问题。

### 8.2 Artifact 和验证协议

v2 使用独立 artifact，不迁移或覆写 v1：

- `vocab_version=2.0`，特殊 token 固定为 `PAD/UNK/NA/BOS/EOS/SESSION_BREAK`；
- checkpoint 标记 `fm_artifact_version=2.0`；
- 加载/续训严格核对 schema、vocab SHA-256、完整有序 FieldSpec、input/target 字段、loss targets；
- 连续 normalizer、盘口状态时序、context horizon 和 pooling 版本写入 checkpoint；
- 25M/100M 实验共享同一 `validation_windows.json`，其内含 manifest fingerprint 和窗口参数；数据或窗口契约改变时直接拒绝复用。

训练进度现在以 `micro_step`、`update_step`、`samples_seen` 和跨 rank 汇总的
`non_pad_tokens_seen` 分开记录；只有成功参数更新才推进 update/sample/token，FP16 overflow
跳步不计入；LR、日志、验证和定期存盘按 update 驱动。token-budget-only 训练必须给出
固定 `optim.lr_schedule_steps`。`step*.pt` 与
`final_resume.pt` 含 optimizer/scaler，`best.pt` 与 `final.pt` 是不含 optimizer 的推理/评估
权重，训练入口拒绝用后两者 resume。当前 `--resume auto` 只选择 `step*.pt` 或
`final_resume.pt` 并优先定期点，继续正常结束的 run 应显式指定
`final_resume.pt`。

MoE artifact 是另一套 `regime_moe_v1` serializer，记录 Regime 配置、normalizer、数据截止
日和 base model hash；当前 loader 仅做版本校验并返回 payload，尚不能单独重建整个
aggregator/model。Backbone-MoE 则随 FM checkpoint 保存 `backbone_moe` 配置。

旧 v1 checkpoint 保持 `legacy_sum` 和原特殊 token 语义，现有 Pilot/Medium/300M/OOS 脚本不会因 v2 模块存在而自动切换。

### 8.4 回归结果

```bash
uv run python -m pytest -q
# 243 passed, 2 skipped, 1 xfailed
```

覆盖重点包括：

- 撤单后活动索引、价格档和 FIFO 一致；全量回放与每个在线前缀状态一致；
- v2 分箱不因 shard 路径顺序变化，重复分位点不会伪造 bin，全流 occupancy 正确；
- v1 checkpoint 无融合元数据仍可加载，v2 vocab hash/字段顺序不匹配会失败；
- Loss 的 NA/ordinal/熵归一化和全无效样本保持有限值；
- 固定验证计划可复用且能检测 manifest 漂移；
- `last/last-k` 跨 chunk 正确，多尺度池化和日内聚合保持因果；
- 行业上下文严格排除自身，PIT 行业映射和未来 interval 不影响过去表示。
- micro/update/token 状态恢复、shard 聚簇分片、RoPE cache、causal fast path 和
  inference checkpoint round-trip；
- Temporal/Backbone MoE 的基本 shape、梯度、辅助损失、padding 排除和评估模式低
  capacity 下的 batch-size independence；
- CPU 上真实执行一个 optimizer update，并核对训练计数和 resume/inference 产物分流。

MoE 回归的边界同样重要：训练模式发生 capacity overflow 时，同 batch 样本会竞争专家
容量，Backbone 的全部有效 `[B,L]` token 也一起竞争；评估/推理模式已改为不裁剪并通过
batch-size independence 测试。这消除了推理时的 batch-size 漂移，但训练期 overflow、
train/eval dispatch 差异、router telemetry 和真实收益仍未验证。

### 8.5 尚未完成与下一验收

1. 生成真实全市场 `cn_l2_v2`、`vocab_v2.json`、tokens 和 manifest，并对盘口快照逐档一致率、NA/UNK、bin occupancy 做数据验收；
2. 使用同一固定验证计划运行 25M 消融，按 per-field CE、unigram/copy baseline、归一化 CE、梯度范数和下游 IC 选择 winner；
3. 仅将 winner 放大到 100M，禁止一开始同时放大模型和数据/目标设计；
4. 冻结 winner 后重抽多尺度 embedding，运行新的 untouched OOS、成本敏感性和风险归因；
5. 单独消融 `IntradayAggregator`、`TemporalRegimeMoE` 与 `cross_asset`，先补 PIT 特征构建、
   telemetry 和完整 artifact loader，再确认增益；
6. 只有轻量 Regime-MoE 多 seed 晋级且训练期 capacity 行为可接受后，才评估顶部
   Backbone-MoE 的吞吐、路由健康度和 FSDP 恢复。

因此，本阶段可确认的是“代码接口和因果/兼容不变量通过回归”，不能确认“年化收益、Sharpe 或最大回撤已经改善”。
