## 二、MinIO 读写 Infra（做了什么）

### 2.1 解决的核心问题

前期阻塞主要来自环境与路径，而非模型本身：

- 示例地址 / 示例 bucket 与机房实际不一致
- 读端与写端端口、权限分离，需独立配置
- 原始数据体量大（约 **4 TiB**），不能整盘落地

因此本阶段重点不是「再写一个清洗脚本」，而是**把读写固化成可运维基础设施**。

### 2.2 已落地能力

```text
【读】机房 MinIO :9000 / zeus-cn-quote
        原始 L2（成交 + 委托）
              │
              ▼  Polars 流式读取 + 订单簿重建
        本地 transient 加工
        （events → tokens → vocab / manifest）
              │
              ▼
【写】机房 MinIO :9100 / model-cache
        fm-pretrain/khalil/{规模标签}/
```


| 能力项     | 说明                                    |
| ------- | ------------------------------------- |
| 读写分离    | 读 raw @ `:9000`；写 tokens/产物 @ `:9100` |
| 连通自检    | 一键检查读写 endpoint 是否可达                  |
| 上传 / 下载 | 训练产物可备份到 MinIO，也可按需拉回本机再训             |
| 一键流水线   | 支持「只做数据」或「数据 + 多卡训练」两种模式              |
| 磁盘策略    | 按日处理、本地临时落盘，避免全量原始数据占满机器              |
| 断点续跑    | 日期 `.done` / `.clean_done`；标的级跳过已有 `events.parquet`；events/tokens 文件级跳过 |
| 并行清洗    | `CLEAN_WORKERS` 多进程按标的并行订单簿重建 |
| **高性能清洗** | `--fast-clean`：每日**单次读取** MinIO + SZ/SH 同池 + 本地 raw 缓存续跑 + 列投影（读取 4 次 → 1 次） |
| 并行规范化  | `CANON_WORKERS` 多进程写 canonical events 分片 |
| 按日 tokenize | reuse-vocab 场景下用**独立子进程**逐日 tokenize（避开 clean 后 spawn 池 fork 死锁）并即时删 events 控盘 |
| 进度查询    | `check_pipeline_progress`：完成天数、当日阶段、ETA；`watch_oos2026_live.sh` 实时看板 |
| 看门狗    | `watchdog_oos2026.sh`：进程死亡自动 `--resume` 续跑；卡死阈值 2h（只在真死时重启，杜绝误杀） |
| 训练续训    | checkpoint 含模型 + optimizer + scaler + step；`--resume auto` |




### 2.3 对业务 / 工程的价值

1. **可复现**：任何人配置密钥后，可用同一套命令复现数据制作过程
2. **可扩展**：从 5 日试跑放大到 60 日全市场，只改模式参数，不改架构
3. **可运维**：读写健康检查、产物路径规范、本地与 MinIO 双存策略清晰

## 三、小 / 中 / 大模型跑通（做了什么）

按「数据规模递增 → 模型规模递增」三级验证，避免一开始就上全市场大训。

### 3.1 三级定义


| 档位    | 数据规模（约定）                        | 模型量级（约）         | 当前状态                               |
| ----- | ------------------------------- | --------------- | ---------------------------------- |
| **小** | 合成数据 smoke；真实数据 pilot（少日 / 少标的） | ~5–15M          | **已跑通**（含 checkpoint、embedding）    |
| **中** | 5 交易日 × 每市场 30 股（medium_try）    | ~80–120M 档试跑    | **已跑通**（完整数据链路 + 8 卡训练 checkpoint） |
| **300M** | 22 交易日 × 沪深全市场（Chinchilla ≈ 6B train events） | ~302M（1024×18） | **数据生产进行中**；管道含并行清洗/断点续跑；训练配置与 `--resume auto` 已就绪 |
| **大** | 60 交易日 × 沪深全市场（≈ 总事件量 1/10）     | ~1B 规划档 | **管道与训练配置可扩展**；待 300M 验证后推进 |


> 说明：本项目「大」定义为相对全市场日历的约 **1/10 抽样规模**（60 日 × 全市场），而非一次性吃完 MinIO 上全部交易日。



### 3.2 各档验证内容

**小模型**

- 合成数据端到端：分词 → 预训练 → embedding → 下游 ranker / 回测闸门  
- 真实 MinIO 数据 pilot：清洗 → tokenize → 预训练 → 抽出 stock-day embedding

**中模型**

- 打通真实 MinIO 读入  
- 完成 clean / events / tokens / manifest  
- 完成 **8 卡 FSDP** 预训练，产出可用权重

**大 / 300M 模型**

- 定稿规模估算与推荐规则（按事件量选模型档位，Chinchilla \(D\approx20N\)）  
- 配齐 22 日全市场日期列表、302M 8 卡配置与 `run_minio_300m_pipeline.sh`  
- 落地并行清洗、标的/日期级断点续跑与训练态恢复  
- 后续可按同一 Infra 放大到 60 日 / 1B

## 七、2026 OOS 零泄漏信号 + 高性能清洗（最新进展）

### 7.1 为什么要 2026 数据

300M FM 的 22 个预训练日**撒满整个 2025 年**（最后一天 `2025-12-31`）。要得到「完全晚于训练数据」的样本外（OOS）信号，只能用 **2026 年**——2025 年内任何窗口都与预训练期重叠，存在表征层「软泄漏」。

零泄漏链路：`FM(best.pt, ≤2025)` + `冻结 vocab(2025)` + `Ranker(2025 训练)` → 对 **2026** embedding 前向出 `score`。三者都没见过 2026 的表征与标签，`score(2026)` 是纯时序 OOS 信号。

### 7.2 流动股池（可行性 + 成本）

全市场 5105 只 × 60 连续日的清洗（每日下载 ~2.8 亿行 + 全市场订单簿重建）约需 30–40h 且磁盘吃紧。改用**流动 top-1000 股池**（按 day-1/2 的 L2 token 文件大小排序，SZ 625 + SH 375，覆盖 ~55% 全市场活跃度），清洗提速数倍、磁盘可控，截面仍足够宽、RankIC 依然可信。

- 股池：`quant_fm/data/oos2026_liquid_{sz,sh}.txt`
- 交易日：`quant_fm/data/oos2026_dates.txt`（61 天：60 信号 + 1 末日 fwd_ret）
- panel（次日收益标签）已过滤到同 1000 只，保证 60 天截面一致

### 7.3 关键代码 / 脚本

| 文件 | 作用 |
|------|------|
| `quant_fm/lob_rebuild/clean_day_fast.py` | 高性能清洗（单次读 + 双市场同池 + 本地缓存 + 列投影），见 [阶段 2 文档](pipeline/02_order_book_rebuild.md) |
| `quant_fm/scripts/tokenize_dir.py` | 独立子进程逐日 tokenize（规避 clean 后 spawn 池 fork 死锁） |
| `quant_fm/scripts/build_oos_delivery.py` | 跨期打分：2025 训 Ranker → 2026 前向出 score + RankIC/ICIR/随机基线 |
| `quant_fm/scripts/make_adhoc_manifest.py` | 从 tokens 目录**动态**造临时 manifest（单 split、按日期白/黑名单、跳过 sha 加速），供增量抽 embedding |
| `quant_fm/scripts/run_oos2026_incremental.sh` | **增量出 score**：不等 61 天跑完，对「已完成整天」滚动抽 embedding→打分，先交付首版信号，后续天补齐自动覆盖 |
| `quant_fm/scripts/run_oos2026_downstream.sh` | 一次性编排（等全量 manifest → 多卡抽 2026 embedding → 跨期打分），与增量版二选一 |
| `quant_fm/scripts/watchdog_oos2026.sh` | 看门狗（串行）：死亡自动续跑、卡死阈值 2h、启用 `--fast-clean` |
| `quant_fm/scripts/run_medium_parallel_days.sh` | **跨日并行驱动**（P0-2）：日期切 `NGROUPS` 份并发跑 `run_medium`，各组 `--skip-manifest`，末尾统一建一次 manifest |
| `quant_fm/scripts/watchdog_oos2026_parallel.sh` | 并行看门狗：监督并行驱动，崩溃/卡死自动 `--resume` 重启，全部完成退出 |
| `quant_fm/scripts/watch_oos2026_live.sh` | 交互终端实时看板（进度条 / 各层存活 / 当前阶段 / 磁盘） |

### 7.4 产出

`quant_fm/runs/oos2026/delivery_oos/`：
- `scores/oos.parquet` —— `date, symbol, score`（2026 全部信号日、每股每日）
- `oos_metrics.json` —— 2026 RankIC / ICIR / 随机基线（真正可信的样本外指标）
- `delivery_manifest.json` —— 版本 / 可复现清单

**增量交付**（`run_oos2026_incremental.sh`）：上面的 `delivery_oos/` 会在累计已抽 ≥ `MIN_DAYS`（默认 15）个交易日后**先出第一版**，此后每有新天完成 tokenize 就**覆盖更新**，直到 60 个信号日全部补齐。这样 score 的首次产出时间从「全部跑完」提前到「~1/4 跑完」。累积 embedding 存于 `embeddings/incr/oos_all.parquet`，账本 `embeddings/incr/embedded_dates.txt`（已抽天，绝不重抽）。

> 说明：`2026-01-05/06` 是选流动股池用的**全市场**样本（各 ~5065 分片），`01-07` 起为 liquid ~1000；打分与 liquid panel 内连接，最终打分股池恒为 liquid∩当日可得，跨天一致。

### 7.5 P0-2 跨日并行清洗（实测 2.13× 提速）

各交易日的 `clean/<date>`、`raw_cache/<date>`、`data/.done/<date>`、
`tokens/<market>/<symbol>/<date>.parquet` 全部按 `<date>` 分文件 → **不同日期天然不冲突**，
故无需改 `run_medium` 核心逻辑，只要把日期切成 `NGROUPS` 份、并发跑多个 `run_medium --resume`。

**64 核基准测试**（liquid 1000 只/天，无其他负载）：

| 架构 | 处理量 | 耗时 | 吞吐 |
|------|-------|------|------|
| 旧（单进程，`CLEAN_WORKERS=32`） | 1 天 | 470s | 7.7 天/时 |
| 新（`NGROUPS=2`，各 `CLEAN_WORKERS=30`） | 2 天 | 441s | 16.3 天/时 |

**加速比 ≈ 2.13×**：2 天并发（441s）比旧架构单天（470s）还快——一天的 MinIO 读（I/O）
与另一天的订单簿回放（CPU）相互重叠，且用满 60 核（旧架构只用 32、留一半空闲）。
核数预算：`NGROUPS × CLEAN_WORKERS ≤ nproc`（64 核建议 2×30）。

配套改动：`run_medium` 新增 `--skip-manifest`（并行组跳过收尾 manifest，由驱动统一建一次）；
并修复收尾 leftover-tokenize 清扫**只扫本组日期**（否则多组共享 `events/` 会撞上别组正在写/删的分片）。

> 两处测试期发现并修复的坑：① `GROUPS` 是 bash 保留只读变量（用户 GID 数组），
> 误用会取到 GID（几百）而启动海量进程 → 改名 `NGROUPS` 且加 1..16 防呆校验；
> ② 跨组 tokenize 竞态（见上）。

### 7.6 复盘：为什么一度空转 12h（经验教训）

1. **看门狗误杀**：清洗订单簿重建阶段本就静默 30–40 分钟，旧阈值 30 分钟把健康进程当卡死反复重启 → 每次重启重下 2.8 亿行 → 恶性循环。**已修**：阈值提到 2h，原则改为「只在进程真死时重启」。
2. **spawn 池 fork 死锁**：clean 后残留上百线程/上百 GB 内存的进程再开 `ProcessPoolExecutor(spawn)`，fork+exec 瞬间被拖死。**已修**：每日 tokenize 改独立子进程（`tokenize_dir.py`）。
3. **重复 IO / 无缓存**：即 `--fast-clean` 解决的双读 + 重启重下问题。
